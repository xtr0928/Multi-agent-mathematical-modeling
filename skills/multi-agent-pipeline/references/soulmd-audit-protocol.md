# SOUL.md 审计与同步协议

> 2026-07-27，基于 SOUL.md 全量审计实战总结。

## 审计清单

对 SOUL.md 逐段审计时，按以下维度检查：

| 维度 | 检查内容 |
|------|---------|
| **同步性** | skill 文件的架构描述是否与 SOUL.md 一致？模型名称/角色是否最新？ |
| **完整性** | 自建的工具/能力（delegate_task, clarify, browser_vision）是否在 SOUL 中有使用指引？ |
| **特殊性** | 平台特有坑（Windows/git-bash/MSYS）是否被记录？ |
| **防御性** | "不编造结果""不自主暂停""逃生口"等信任底线是否多次强化？ |
| **入口覆盖** | 架构选择逻辑表是否覆盖所有常用场景（含 APK 取证等垂直领域）？ |

## 常见脱节信号

以下任一出现，说明 SOUL.md 需要同步：

- skill 文件改了 Phase 流程，SOUL.md 还是旧版本
- 新增了 Profile 或改了模型，SOUL.md 模型表未更新
- 用户问"为什么你没用 X 工具"——X 在 skill 里有但 SOUL 没提
- 同样的问题在不同 session 反复出现——规则没进 SOUL

## 修改优先级框架

```
P0: 会导致行为错误（模型名称/流程不一致）
P1: 会导致效率显著下降（工具未提及、超时规则缺失）
P2: 特定场景下会踩坑（平台特殊性、触发词不全）
P3: 锦上添花（格式统一、文档策略）
```

## clarify 工具使用规范

- **附带优缺点**：每个选项说明 tradeoff，让用户做知情决策
- **保留"其他"**：永远利用 clarify 自带的自定义输入口
- **选择题 vs 开放题**：技术选型/范围/是否 → clarify；解释/讨论 → 自然语言
